## Qué cambió

- Los 10 alias españoles del CLI (`--limite`, `--titulo`, `--contenido`,
  `--nota`, `--refresca`, `--crea`, `--min-similitud`, `--escala-fts`) ya no
  parsean. `engine` → `0.2.0`.
- `plugins/exo/ENGINE_MIN` **se queda en `0.1.0`** (decisión de Paul, tras la
  review final de H, 2026-09-15): declara lo que el plugin 1.2.0 necesita de
  verdad, y ningún script del plugin usa nada de engine 0.2.0 — la retirada
  de aliases es una ruptura para quien invoque el CLI con los flags
  españoles, no para el plugin. El mecanismo (`ENGINE_MIN`, el helper
  `_engine-version.sh`, la rama `engine-stale` de `exo-recall.sh`, el check
  `plugin_compat` de `exo doctor`, el gate de `scripts/test-versiones.sh`)
  queda construido y probado; sube el día que algún script del plugin use
  algo que exija engine 0.2.0 o posterior. `recall-inject.sh`
  (UserPromptSubmit, corre en cada prompt) NO lleva este check — decisión de
  Paul en pre-flight de H: un `exo --version` por prompt sería un spawn
  extra en conflicto con la latencia del hook que mide la campaña I. Solo
  `exo-recall.sh` y `exo doctor` conocen `ENGINE_MIN`.
- `plugin.json` / `marketplace.json` → `1.2.0`.

## Orden de publicación: mergear a `main` y el tag `v0.2.0` son independientes

Con `ENGINE_MIN = 0.1.0`, mergear esta rama a `main` publica el plugin
`1.2.0` de inmediato (el marketplace de Paul es `github:
pguerrerolinares/exo`, así que un merge a `main` es una publicación) **sin
degradar a nadie** que siga con el binario `0.1.0` instalado: el check
`plugin_compat` de `exo doctor` compara contra `ENGINE_MIN`, que sigue en
`0.1.0`, así que cualquier binario `>= 0.1.0` sigue saliendo `ok`. No hace
falta acoplar el merge a la publicación del tag.

El tag `v0.2.0` y su release (línea roja de Paul: nunca la ejecuta un
consultor ni un executor) son para quien invoque el CLI con los flags
españoles retirados — ese SÍ necesita el binario nuevo para no romperse.
`install.sh`/`install.ps1` piden `latest` por defecto y seguirán instalando
`v0.1.0` hasta que ese tag exista.

Si en el futuro algún script del plugin empieza a depender de algo de
engine 0.2.0 (o posterior), ESE es el momento de subir `ENGINE_MIN` — y
entonces sí aplica instalar el binario correspondiente antes de publicar
ese plugin:

1. Compila e instala el binario primero
   (`cd engine && cargo build --release`, copia a
   `~/.local/bin/exo(.exe)`).
2. Corre `exo doctor` — el check `plugin_compat` debe salir `warn` (todavía
   no hay ese plugin en caché) o `ok` (si ya lo hay), nunca `fail`.
3. Solo entonces publica el plugin que sube `ENGINE_MIN`.

## Aviso: `kb-precommit.sh` es fail-closed

En una máquina sin `exo` instalado (p. ej. la Linux del checklist de abajo),
en cuanto el hook de pre-commit de la KB resuelva al script `1.2.0`
(campaña H, Task 6, con el fallback al `$PATH` añadido en la review final,
I2), los commits de esa KB quedan **BLOQUEADOS** — ya no hay degradación
silenciosa. Remedio: instalar `exo` (`install.sh`/`install.ps1`, o
cualquier ruta del `$PATH`) o `git commit --no-verify` como escape
consciente (el propio mensaje del hook ya lo dice).
