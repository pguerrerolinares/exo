## Antes de tocar nada: la red de rollback

```bash
mkdir -p ~/.local/backups/m6-04
cp ~/.local/bin/kbx ~/.local/backups/m6-04/kbx-pre-m6-04
cp ~/.local/bin/exo ~/.local/backups/m6-04/exo-pre-m6-04
```

`kbx --version` no distingue builds, igual que `exo --version` está fijo en
`0.1.0`. La red es la copia del binario, no la versión.

## Paso 1 — Instalar exo (primero, y no es cosmético)

`meta` solo existe cuando el binario **nuevo** de exo corre `exo index`. Si
instalas kbx antes, kbx se queda sin `kb_root` y todos los comandos exigen
`--kb`. Este orden es el mismo motivo por el que en C9 el binario instalado
corrió 20 h por detrás de su propio fix sin que nada avisara: el canary de
`doctor` (Paso 4) solo vigila la desincronización *entre* exo y kbx si exo va
primero.

```bash
cd /home/paul/Documentos/proyectos/exo/engine && cargo build --release
cp target/release/exo ~/.local/bin/exo
exo index --kb ~/Documentos/proyectos/kb-demo --db ~/.exo/index.db --json
```

Esperado: el comando termina con exit 0 e imprime un envelope JSON con
`data.indexadas` > 0. Si falla o `indexadas` es 0, **para aquí** — no sigas al
Paso 2 con un índice a medias — y ve directo al rollback del Paso 4.

## Paso 2 — Verificación falsable del índice

```bash
python3 -c "
import sqlite3
c = sqlite3.connect('file:$HOME/.exo/index.db?mode=ro', uri=True)
print('kb_root =', c.execute(\"SELECT valor FROM meta WHERE clave='kb_root'\").fetchone())
print('journal =', c.execute('PRAGMA journal_mode').fetchone()[0])
"
```

Esperado: `kb_root = ('/home/paul/Documentos/proyectos/kb-demo',)` y
`journal = wal`. Un `kb_root` vacío o `journal = delete` significa que el
binario instalado es el viejo — es el gotcha de las 20 h de C9, repetido. Si
sale así, **no instales kbx todavía**: repite el Paso 1 (revisa que
`cargo build --release` haya compilado de verdad la rama `m6-04`, no `main`)
antes de continuar.

## Paso 4 — Verificación falsable de kbx

```bash
kbx doctor --json | head -20
kbx targets "memoria" --json --limit 5
```

Esperado: ambos responden **sin `--kb` ni `--db`**, con un JSON válido (no un
error de "falta --kb"). Si `doctor` reporta `schema_drift`, el canary está
haciendo su trabajo: uno de los dos binarios va atrasado — vuelve al Paso 1 o
al Paso 3 según cuál sea el atrasado, no ignores el finding.

**Nota — findings nuevos que no son regresión:** la Task 10 de esta campaña
quitó el filtro `tipo='note'` de kbx. A partir de este cutover `kbx targets`
verá **57 notas más** que antes (no excluye por directorio) y `kbx doctor` /
`kbx stale` verán **23 findings más** (el subconjunto de esas 57 que además
vive fuera de los directorios que `doctor`/`stale` sí recorrían). Si tras
instalar ves esos números subir, es el cambio esperado del port, no una
avería — no lo trates como regresión ni empieces a waivearlo a ciegas.

Rollback si algo va mal:

```bash
cp ~/.local/backups/m6-04/kbx-pre-m6-04 ~/.local/bin/kbx
cp ~/.local/backups/m6-04/exo-pre-m6-04 ~/.local/bin/exo
```

El rollback de kbx revierte el port entero: no hay grano fino. Tras
rollbackear, repite el Paso 2 contra el índice: si sigue en `wal`/`kb_root`
poblado, el índice no vuelve solo al formato viejo — no es necesario (ni
posible) revertirlo, kbx viejo simplemente no lo lee (exigirá `--kb`/`--db`
explícitos como antes). Si necesitas volver también al índice de
basic-memory, ese binario y esa DB no se han tocado — están donde estaban.

## Paso 5 — `/consolida` de humo

Corre `/consolida` una vez. Es el consumidor que falla-fuerte ante
`schema_drift`, así que es la prueba de integración real del canary.

Esperado: `/consolida` progresa más allá del Paso 1 (budget check) sin
abortar con el mensaje de `schema drift` del Paso 1 de esa skill. Si aborta
ahí, es el mismo canary del Paso 4 disparándose en el consumidor real —
diagnostica con `kbx doctor --json` antes de nada más.
